## Номер версии
- Из метки vX.Y.Z: versionName = X.Y.Z, versionCode = X·1 000 000 + Y·1 000 + Z. Примеры: 0.0.2 → 2, 0.1.0 → 1000, 1.2.3 → 1002003.
- Без метки (локальная сборка): 0.0.0-dev, код 1. Неверный формат (например 1.2) сборка отклоняет.
- CI проверяет расчёт на трёх примерах и отказ на неверном.

## Подпись
- Ключ: RSA 4096, хранилище PKCS12, имя `pogodaapp`, пароль ключа равен паролю хранилища, действует до 2054-03-15.
- Отпечаток сертификата (SHA-256): `babb4c4018cd6e5f1db86ee3668eb993f9f97dd6dafaca1d6c26c31a05dbe507`.
- В GitHub два секрета: `KEYSTORE_PASSWORD` и `KEYSTORE_BASE64` (файл ключа в виде одной строки). Имя ключа лежит в сценарии выпуска.
- Для minSdk 36 Gradle подписывает релиз схемой v3 (v2 не нужна); проверка в CI требует v3.
- Сценарий `prepare_keystore.sh` проверяет секреты, раскодирует ключ, сверяет `keytool -list`, после выпуска ключ удаляется с машины.
- Сверка ключа с прошлым выпуском (`key_continuity.py`): отпечаток записан в тексте каждого релиза; если новый ключ другой, выпуск падает. Это защита от потери ключа: обновления с другим ключом у друзей не встанут.
- Файлы ключа в репозиторий не попадают (.gitignore). Сам ключ и пароль в документы и память не записывать.

## Что проверяет CI (каждый push)
1. Тесты сценариев выпуска (8 проверок сверки ключа; сценарий `make_cache.py` для эмулятора тоже с тестом).
2. Линт (в том числе правила Compose, ошибки останавливают сборку), модульные тесты приложения, сборка debug. Предупреждения компилятора считаются ошибками.
3. Разбор debug-APK: пакет, версия, minSdk/targetSdk, иконка (в том числе одноцветная), локали ru и de, разрешения (допустимы `INTERNET`, `ACCESS_COARSE_LOCATION` и внутреннее разрешение приёмника; любое другое останавливает проверку), подпись.
4. Расчёт versionCode.
5. Пробный выпуск с одноразовым ключом через тот же `prepare_keystore.sh`: сборка с R8 и сжатием ресурсов, разбор APK, подпись v3.
6. Эмулятор Android 16 (Pixel 6 Pro, API 36, анимации выключены), сценарий `emulator_smoke.sh`:
   - без разрешения на местоположение: карточка «Разрешить» на en, ru, de;
   - настоящее системное окно разрешения: отказ, повторный отказ, кнопка «Открыть настройки» ведёт в системные настройки приложения; затем разрешение;
   - с разрешением и сетью: настоящий прогноз Open-Meteo (если сеть эмулятора недоступна, это предупреждение, не ошибка);
   - без сети с сохранённым прогнозом: данные и строка «Нет сети · данные 3 часа назад» на en, ru, de;
   - обновление протягиванием вниз (пункт 3б, с версии 0.1.2): короткое движение не обновляет, длинное обновляет, во время обновления верх экрана сдвинут на 56 dp и у индикатора подпись, потом всё возвращается;
   - небо (пункт 3в, с версии 0.2.0): сценарий открывает скрытый экран проверки семью нажатиями на номер версии, по очереди ставит шесть времён суток и семь видов погоды (кнопки на экране), на каждом состоянии сверяет, что в строке «Картины» названа нужная картина, и снимает экран при свёрнутой панели; затем включает анимации (на эмуляторе их выключает сам запуск), кнопкой «Сбросить» начинает дрейф заново, ждёт 5 секунд, читает положение облаков и каждые 3 секунды сверяет его с первым, пока сдвиг не станет не меньше 0,03 (до 24 секунд; с версии 0.2.1, грубая защита от остановки облаков; точное начало дрейфа проверяет `SkyDriftTest`). Первоначальный вариант ждал 5 секунд, и 29.10.2026 два запуска упали: эмулятор без видеокарты рисует кадр около секунды, строка на экране обновляется редко. Зелёный запуск: сдвиг 0,34 → 0,40 за 6 секунд, читает частоту кадров, потом ставит масштаб анимаций 0 и требует: кадров не больше 3 в секунду, положение облаков не меняется; в конце закрывает экран проверки;
   - рабочая сборка (release, R8): запускается, карточка без разрешения на трёх языках, после разрешения не падает;
   - в журнале нет сбоев;
   - при зависании приложения («isn't responding») или любом другом падении сценарий перед выходом сохраняет `anr.txt` (стек главного потока), `gfxinfo.txt` (кадры отрисовки), `meminfo.txt`, `app-logcat.txt`; в `smoke.log` строки `[память]` и `[небо]`.
7. Снимки экрана каждого состояния и журналы кладутся в ветку `ci-screenshots` (служебная) после проверки любой ветки, в том числе упавшей: `smoke.log` (весь вывод сценария, при сбое ещё `anr.txt`, `gfxinfo.txt`, `meminfo.txt`, `app-logcat.txt`), `logcat.txt` (журнал телефона, последние 8000 строк), `build-debug.log`, `build-release.log`. В `README.txt` записаны коммит и ветка, которым принадлежат файлы (каждая проверка заменяет содержимое ветки). Получить: `git fetch origin ci-screenshots`, `git archive FETCH_HEAD | tar -x -C <папка>`.

Разбор экрана эмулятора идёт по `uiautomator dump` (тексты и описания), нажатия по координатам из разметки. Эмуляторная служба GMS не даёт приближённого места, поэтому в debug-сборке есть файл `files/location_override.txt` с координатами (кладётся через `run-as`); в release-сборке этого кода нет (`app/src/release/.../Locations.kt`). Там же файл `files/location_delay_ms.txt`: число миллисекунд, на которое debug-сборка замедляет определение свежего места (нужен только проверке протягивания). Сохранённый прогноз для проверки «без сети» кладёт `make_cache.py` из ответа-образца (`app/src/test/resources/open-meteo/hannover.json`) в `files/forecast_cache.json`.

## Выпуск версии
Кнопка «Run workflow» (Actions → Release, поле «version», ветка `main`) или метка `vX.Y.Z` запускает `release.yml`: сборка, разбор APK, сверка ключа, публикация `PogodaApp-X.Y.Z.apk` в Releases с текстом из `release-notes/X.Y.Z.md` и отпечатком ключа. Obtainium берёт APK оттуда.

## Устройство приложения на шаге 1
- Пакеты в `app/src/main/kotlin/io/github/dumahuch/pogodaapp/`: `weather` (модель прогноза и коды погоды), `data` (клиент и разбор Open-Meteo, сохранённый прогноз), `location` (определение места, название города), `home` (состояние и ViewModel главной), `ui` (тема, компоненты, экраны).
- Прогноз: `https://api.open-meteo.com/v1/forecast` с текущими значениями, почасовыми (49 значений) и дневными максимумом и минимумом; время в unixtime. Осадки в почасовых данных относятся к предыдущему часу, поэтому для столбца часа T берётся запись T+1. Координаты в запросе округляются до 0,01° (около 1 км). Заголовок User-Agent: `PogodaApp/<версия>`.
- Условия Open-Meteo: данные под лицензией CC BY 4.0; ссылка «Weather data by Open-Meteo.com» на https://open-meteo.com/ должна стоять рядом с каждым местом, где показаны данные (https://open-meteo.com/en/licence). Сейчас она в нижней строке главной; на новых вкладках с данными нужна такая же. Бесплатный доступ только для некоммерческого использования, до 10 000 запросов в день (https://open-meteo.com/en/terms).
- Место: системный `LocationManager`, только `ACCESS_COARSE_LOCATION`. Последнее известное место (`getLastKnownLocation` у FUSED и NETWORK, берётся более новое) отвечает сразу. Свежее место (`getCurrentLocation`) запрашивается у FUSED и NETWORK одновременно, побеждает первый ответивший, общий предел 10 с. Название города через `Geocoder`, если не получилось, «Текущее место».
- Порядок загрузки на главной (с версии 0.1.1): показываются сохранённые данные; прогноз запрашивается сразу по последнему известному месту, не дожидаясь свежего; свежее место определяется параллельно, и если оно дальше 2 км от первого, прогноз запрашивается ещё раз (неудача второго запроса не затирает показанное); название места ищется параллельно с запросом прогноза и дописывается, когда готово (запоздалое название прежнего места не заменяет текущее). До 0.1.0 прогноз ждал свежего места (до 10 с на поставщика подряд), а название ждало прогноза: Дима 28.10.2026 пожаловался, что данные грузятся долго.
- Обновление: при открытии приложения, если данным больше 15 минут или есть ошибка; сохранённый прогноз показывается сразу и лежит в `files/forecast_cache.json`. Название из сохранённого берётся, если место сместилось меньше чем на 2 км.
- Обновление протягиванием (с версии 0.1.2): `HomeViewModel.refresh()` заново определяет место и грузит прогноз, не глядя на 15 минут; флаг `refreshing` держит индикатор, он виден не меньше 700 мс; повторное протягивание во время обновления игнорируется. Жест написан на обычной вложенной прокрутке (`NestedScrollConnection` в `ui/components/PullRefresh.kt`), без пробных функций Material 3 (иначе сборка с «предупреждения как ошибки» требует отдельного допуска, а их стабильность в версии библиотеки не проверена). Порог 64 dp сдвига (палец проходит вдвое больше, около 2 см), удержание 56 dp, предел 100 dp; сдвигается только верхняя часть экрана, лента «По часам» и панель стоят. Проверка на эмуляторе (`emulator_smoke.sh`, пункт 3б): короткое движение (около 45 dp пальцем) обновление не запускает; длинное запускает (по строке `PogodaRefresh` в журнале). Чтобы успеть увидеть обновление, проверочная сборка (только debug) читает из папки приложения файл `location_delay_ms.txt` и на столько миллисекунд замедляет определение свежего места (сценарий ставит 12 000). Пока обновление идёт, проверка требует сдвиг верха экрана на 56 dp и подпись индикатора «Refreshing…», потом возврат на место и исчезновение индикатора. Снимки «3б-…» лежат в ветке `ci-screenshots`.
- Цвета мелкого текста: Ink2; Ink3 не проходит 4,5 : 1 на стекле и небе и мелким текстом не используется (проверяет `PaletteContrastTest`).
- Положение крупной цифры и градуса считается от базовой линии шрифта Manrope так же, как в макете (Compose иначе ставит первую строку по полной высоте шрифта).

## Небо (с версии 0.2.0)
- Логика без Android лежит в пакете `sky` (внутренние классы, проверяются модульными тестами на JVM):
  - `SunPosition`: высота солнца и солнечное время места по приближённым формулам Астрономического ежегодника (USNO, https://aa.usno.navy.mil/faq/sun_approx, точность около угловой минуты в пределах двух веков от 2000 года). Формулы NOAA (ряд Спенсера, https://gml.noaa.gov/grad/solcalc/solareqns.PDF) пробовали первыми: у них склонение уходит до 0,45° (около суток), тест с независимой библиотекой astral 3.2 их не пропустил. Тест `SunPositionTest` держит допуск 0,05° на восьми точках мира.
  - `SkyScene`, `SkyTimeOfDay`: шесть картин и их доли по высоте солнца (не по часам); `SkyState` оставляет не больше двух самых весомых картин, чтобы в памяти было не больше двух времён суток.
  - `SkyWeather`, `SkyColors`: вид погоды (семь видов) и цвета погодной вуали по таблице макета.
  - `SkyMaps`: карты яркости 192×128 для всех 12 картин одним файлом `assets/sky/maps.bin` (1,2 МБ); делает `design/sky/tools/make_maps.py` из WebP. `SkySampler` собирает по ним кадр 41×89 теми же шестью слоями, что рисует экран, и снимает цвета под цифрами, предупреждениями, карточкой и нижней панелью (кадр с экрана не читается).
  - `SkyTheme`, `SkyThemeDriver`: тёмный или светлый текст и плотность стекла по формулам макета; цвет текста меняется, только если другой вариант лучше на 0,6 балла, и плавно (3,2 в секунду); сглаживание цветов фона при дрейфе облаков (доля 0,4).
- Экран, пакет `ui/sky`: `SkyHost` (считает небо по месту, времени и погоде, рисует его под экраном, раздаёт цвета через `LocalPogodaPalette` и `LocalContentColor`, управляет памятью и обновлением), `SkyPainter` (рисование: картины каскадом → погодная вуаль → облака → обесцвечивание цветовой матрицей → затемнение → приглушение света облаков; подложка под большими цифрами), `SkyBitmapStore` (аппаратные изображения через `ImageDecoder.ALLOCATOR_HARDWARE`, не больше двух времён суток, выгрузка при уходе приложения с экрана), `AnimationsEnabled` (небо стоит при экономии энергии, при `ValueAnimator.areAnimatorsEnabled() == false` и при масштабе анимаций 0; отслеживается слушателями), `SkyCheck` (экран проверки), `TapSequence` (семь нажатий подряд, не больше 1,5 с между ними), `FrameStats` (счётчик кадров по `Window.OnFrameMetricsAvailableListener`).
- Облака обновляются 20 раз в секунду, цвета интерфейса 4 раза в секунду (33 мс шаг, пока меняется цвет текста). Пока прогноза нет, фон нейтральный градиент шага 1; небо и цвета интерфейса проявляются вместе за 0,6 с.
- Сверка с макетом: `app/src/test/resources/sky/golden.json` хранит 126 состояний (9 моментов × 7 видов погоды × 2 фазы облаков), снятых с макета версии 21 в браузере; `SkyGoldenTest` сверяет доли картин, цвета вуали, оценки текста и цвета интерфейса (допуск 1e-6 для формул, для снятых с картин цветов 8 в среднем и 14 в пятнах из 255). `SkyReadabilityTest` проверяет читаемость на 15 моментах × 7 видах погоды × 4 положениях облаков: цифры не ниже 3, карточки, оповещения и кнопки не ниже 4 : 1.
- Вид кадра на эмуляторе сверен с макетом на тот же час: совпадает по цвету и составу.
- Начало дрейфа (с версии 0.2.1): положение облаков `AMPLITUDE·sin(фаза + 7,7)`, фаза растёт со скоростью `2π / период`. Старая начальная фаза 0 ставила облака к краю хода: скорость около 15 % от наибольшей, разворот через 3,7 с, при штиле первые десять секунд медленнее 4 пикселей в секунду, до половины скорости 16 секунд. Это и видел Дима 29.10.2026 («анимация начинается не сразу»). Теперь `SkyDrift.START_PHASE = 3π − 7,7`: старт из середины хода на наибольшей скорости (при штиле около 16 пикселей в секунду на Pixel 6 Pro), за первые десять секунд проходится 0,86–0,97 пути на наибольшей скорости (раньше 0,06–0,30). Проверяет `SkyDriftTest` (пять проверок на JVM) и пункт 3в эмуляторного сценария.
- Замер загрузки картин (с версии 0.2.1): `SkyBitmapStore.lastLoad` хранит число загруженных картин, время первой и всех; значение пишется в журнал (`Log.i`, метка `PogodaSky`) и показывается строкой «Загрузка картин» на экране проверки. Нужен, чтобы по цифрам с телефона решить, задерживает ли показ неба декодирование (при запуске и при возвращении в приложение картины декодируются заново, пока видно нейтральный фон). Исправление по этой причине (параллельное декодирование, выдержка перед выгрузкой, «липкая» готовность) не сделано, пока нет цифр.
- Скрытый экран проверки есть и в рабочей сборке: он не влияет на данные, при закрытии возвращает настоящие время и погоду.

## Стекло (с версии 0.2.2)
- Решение Димы: вид «Авто» по макету (подробности в документе решений). Код: `ui/components/Glass.kt`; цвета: `sky/SkyTheme.kt` (`glassHighlight`, `buttonHighlight`, `shadow`, `smoke`), `ui/PogodaPalette.kt`, `ui/sky/PaletteBridge.kt`; хозяин размытия `ui/sky/SkyHost.kt` (`hazeState`, `rememberGlass`, `LocalGlass`, `hazeSource` на небе).
- Размытие: Haze 2.0.1 (`dev.chrisbanes.haze:haze` и `:haze-blur`, разбор исходников в клоне; на Android размытие идёт через `RenderEffect`, API 31+). Радиус 10 dp, режим по умолчанию (средний). Порядок действий библиотеки: размытие, зерно (режим Softlight), цветовые эффекты. Карточки: яркость 1 − 0,15·k, насыщенность 1,6 + 0,4·k, зерно 0,10 + 0,06·k, где k это положение переключателя текста (`SkyPalette.smoke`, квантуется на 20 шагов, чтобы не пересоздавать стиль). Кнопки и нижняя панель: насыщенность 1,6, зерно 0,08.
- Тени своим кодом, потому что `dropShadow` Compose не вырезает внутренность формы (сквозь прозрачное стекло просвечивала бы тень) и не знает отрицательного расширения. Семь слоёв тени карточки (`--sh3d`), пять слоёв блика по кромке (`--rim`), тень кнопок `0 8px 20px -10px`. Размытие CSS радиуса B это сигма B / 2; маска Skia `BlurMaskFilter` берёт радиус (сигма − 0,5) / 0,57735. Числа слоёв сверяет `GlassTest` с `design/mockup/src/style.css` (пропускается, если файла нет).
- Тонкая светлая линия по верхней кромке (`topHighlight`) это форма минус она же, сдвинутая на 1 dp вниз, обычная заливка.
- Как тени рисуются (важно): `RasterShadowNode` один раз на фоновом потоке рисует все слои в растр `ALPHA_8` (карта прозрачности) и выводит его с цветом через `ColorFilter.tint`; растр пересчитывается только при смене размера, плотности, формы и слоёв; пока он не готов, тени нет. Так видеокарта не размывает тени каждый кадр.
- Находка при проверке на эмуляторе (29.10.2026): первая версия рисовала тени маской `BlurMaskFilter` прямо на холсте экрана. На эмуляторе без видеокарты (SwiftShader) кадр занимал около 4,95 с (`gfxinfo`: 3 кадра, все с задержкой), главный поток ждал отрисовочный (`HardwareRenderer.setStopped`), и система выдавала «PogodaApp isn't responding» (сначала в сценарии ru, потом en). Размытие Haze при этом осталось, и проверка прошла (коммит 8990afc; эмулятор рисует кадры редко, 2,4 в секунду, это не оценка телефона). Вывод: виновата была цена масок тени на каждом кадре; Haze на эмуляторе укладывается. Как поведёт себя Haze на Pixel, покажет замер Димы.
- Тесты: `SkyGlassPaletteTest` (цвета блика, тени, дымчатость), `GlassTest` (маска, `grown`, слои тени и блика против CSS макета).
- Не входит: виды «Лёгкое» и «Дымчатое 3D» как режимы, оповещения (их ещё нет), эффекты погоды на карточках.

## Не проверено
- Небо на живом Pixel: Дима 29.10.2026 проверил 0.2.0 на Pixel 6 Pro и Pixel 7 (всё работает, замечание про поздний старт облаков исправлено в 0.2.1, исправление ещё не проверено им). Не проверены: расход батареи и памяти, смена цвета значков системных панелей, поведение при Battery Saver, цифры «Загрузка картин» при холодном запуске и при возвращении в приложение. Эмулятор без видеокарты рисует кадр за сотни миллисекунд, поэтому частоту кадров на нём судить нельзя; цифры даёт счётчик на экране проверки на телефоне.
- Стекло (0.2.2) на живом Pixel: частота кадров и плавность прокрутки ленты «По часам» с включённым размытием (счётчик на экране проверки), расход памяти на растры теней, вид стекла на разных небах. Если кадры хуже, пробуем: меньшее качество размытия Haze (`HazePerformanceMode`), одну общую подложку вместо трёх размытий, меньше слоёв тени.
- Установка 0.1.0 на живой Pixel, настоящее системное окно разрешения на телефоне Димы, определение места в поле, обновление 0.0.2 → 0.1.0 через Obtainium.
- Обновление протягиванием (0.1.2) на живом Pixel: ощущение жеста, порог (около 2 см пальцем), вид индикатора. Эмулятор проверяет работу жеста и положение, но не удобство; смотрит Дима.
- Сверка ключа с прошлым релизом прошла на v0.0.2 (28.10.2026, отпечаток тот же); для 0.1.0 будет прогнана снова.

## Ограничения среды Claude
- Из сессии недоступны Android SDK, Maven и Gradle (403 на узлах Google и Gradle), поэтому настоящий тест сборки делает GitHub Actions.
- Команды `gh release …` из сессии не работают (используют GraphQL, он закрыт, 403): выпуски читать через `gh api repos/dumahuch/weather/releases`.
- Журналы запусков GitHub из сессии не скачиваются: `gh api .../actions/jobs/<id>/logs` перенаправляет на хранилище `*.blob.core.windows.net`, его нет в списке разрешённых узлов сессии (403). Поэтому проверки сами выкладывают нужные журналы в ветку `ci-screenshots` (пункт 7 выше). Расширить список узлов можно в настройках среды (claude.ai/code → меню у названия сессии → «Edit cloud environment» → Network access → Custom), но это открывает любые хранилища Azure, поэтому не сделано.
- Запросы к API запусков Actions, отправка меток и удаление веток и меток через сессию запрещены (403). Результаты читаются через проверки коммита: `repos/dumahuch/weather/commits/<sha>/check-runs` и их аннотации (сценарий `annotate_failure.py` выводит причины падения в аннотации).
- Ветка `ci-probe` осталась от пробного запуска, Claude удалить её не может. Дима может удалить сам: GitHub → Branches → корзина у `ci-probe`. Ветки `design-materials` и `step-1` (слиты в main) тоже не удалены. Ветка `ci-screenshots` служебная (снимки экрана проверок), создаётся заново при каждой проверке ветки `step-*`.

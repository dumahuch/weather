## Версии инструментов
- Android Gradle Plugin 9.4.1 со встроенным Kotlin (отдельного плагина kotlin.android нет), плагин Compose 2.4.21, Gradle 9.7.1 (в обёртке проверочная сумма), Java 21 на сборке.
- Compose BOM 2026.09.00, activity-compose 1.13.0, Material 3.
- minSdk 36 (Android 16), targetSdk 36, compileSdk 37: Compose 1.12 требует API 37 при компиляции. Предупреждения Kotlin считаются ошибками.
- Языки en, ru, de (localeFilters и locales_config.xml). Только портрет.
- Debug-сборка ставится рядом с настоящей: пакет `…pogodaapp.debug`, версия с суффиксом `-debug`.

## Номер версии
- Из метки vX.Y.Z: versionName = X.Y.Z, versionCode = X·1 000 000 + Y·1 000 + Z. Примеры: 0.0.2 → 2, 0.1.0 → 1000, 1.2.3 → 1002003.
- Без метки (локальная сборка): 0.0.0-dev, код 1. Неверный формат (например 1.2) сборка отклоняет.
- CI проверяет расчёт на трёх примерах и отказ на неверном.

## Подпись
- Ключ: RSA 4096, хранилище PKCS12, имя `pogodaapp`, пароль ключа равен паролю хранилища, действует до 2054-03-15.
- Отпечаток сертификата (SHA-256): `babb4c4018cd6e5f1db86ee3668eb993f9f97dd6dafaca1d6c26c31a05dbe507`.
- В GitHub два секрета: `KEYSTORE_PASSWORD` и `KEYSTORE_BASE64` (файл ключа в виде одной строки). Имя ключа лежит в сценарии выпуска.
- Для minSdk 36 Gradle подписывает релиз схемой v3 (v2 не нужна); проверка в CI требует v3.
- Сценарий `prepare_keystore.sh` проверяет секреты, раскодирует ключ, сверяет `keytool -list`, после выпуска ключ удаляется с машины.
- Сверка ключа с прошлым выпуском (`key_continuity.py`): отпечаток записан в тексте каждого релиза; если новый ключ другой, выпуск падает. Это защита от потери ключа: обновления с другим ключом у друзей не встанут.
- Файлы ключа в репозиторий не попадают (.gitignore). Сам ключ и пароль в документы и память не записывать.

## Что проверяет CI (каждый push)
1. Тесты сценариев выпуска (8 проверок сверки ключа; сценарий `make_cache.py` для эмулятора тоже с тестом).
2. Линт (в том числе правила Compose, ошибки останавливают сборку), модульные тесты приложения, сборка debug. Предупреждения компилятора считаются ошибками.
3. Разбор debug-APK: пакет, версия, minSdk/targetSdk, иконка (в том числе одноцветная), локали ru и de, разрешения (допустимы `INTERNET`, `ACCESS_COARSE_LOCATION` и внутреннее разрешение приёмника; любое другое останавливает проверку), подпись.
4. Расчёт versionCode.
5. Пробный выпуск с одноразовым ключом через тот же `prepare_keystore.sh`: сборка с R8 и сжатием ресурсов, разбор APK, подпись v3.
6. Эмулятор Android 16 (Pixel 6 Pro, API 36, анимации выключены), сценарий `emulator_smoke.sh`:
   - без разрешения на местоположение: карточка «Разрешить» на en, ru, de;
   - настоящее системное окно разрешения: отказ, повторный отказ, кнопка «Открыть настройки» ведёт в системные настройки приложения; затем разрешение;
   - с разрешением и сетью: настоящий прогноз Open-Meteo (если сеть эмулятора недоступна, это предупреждение, не ошибка);
   - без сети с сохранённым прогнозом: данные и строка «Нет сети · данные 3 часа назад» на en, ru, de;
   - обновление протягиванием вниз (пункт 3б, с версии 0.1.2): короткое движение не обновляет, длинное обновляет, во время обновления верх экрана сдвинут на 56 dp и у индикатора подпись, потом всё возвращается;
   - рабочая сборка (release, R8): запускается, карточка без разрешения на трёх языках, после разрешения не падает;
   - в журнале нет сбоев.
7. Снимки экрана каждого состояния и журналы кладутся в ветку `ci-screenshots` (служебная) после проверки любой ветки, в том числе упавшей: `smoke.log` (весь вывод сценария), `logcat.txt` (журнал телефона, последние 8000 строк), `build-debug.log`, `build-release.log`. В `README.txt` записаны коммит и ветка, которым принадлежат файлы (каждая проверка заменяет содержимое ветки). Получить: `git fetch origin ci-screenshots`, `git archive FETCH_HEAD | tar -x -C <папка>`.

Разбор экрана эмулятора идёт по `uiautomator dump` (тексты и описания), нажатия по координатам из разметки. Эмуляторная служба GMS не даёт приближённого места, поэтому в debug-сборке есть файл `files/location_override.txt` с координатами (кладётся через `run-as`); в release-сборке этого кода нет (`app/src/release/.../Locations.kt`). Там же файл `files/location_delay_ms.txt`: число миллисекунд, на которое debug-сборка замедляет определение свежего места (нужен только проверке протягивания). Сохранённый прогноз для проверки «без сети» кладёт `make_cache.py` из ответа-образца (`app/src/test/resources/open-meteo/hannover.json`) в `files/forecast_cache.json`.

## Выпуск версии
Кнопка «Run workflow» (Actions → Release, поле «version», ветка `main`) или метка `vX.Y.Z` запускает `release.yml`: сборка, разбор APK, сверка ключа, публикация `PogodaApp-X.Y.Z.apk` в Releases с текстом из `release-notes/X.Y.Z.md` и отпечатком ключа. Obtainium берёт APK оттуда.

## Устройство приложения на шаге 1
- Пакеты в `app/src/main/kotlin/io/github/dumahuch/pogodaapp/`: `weather` (модель прогноза и коды погоды), `data` (клиент и разбор Open-Meteo, сохранённый прогноз), `location` (определение места, название города), `home` (состояние и ViewModel главной), `ui` (тема, компоненты, экраны).
- Прогноз: `https://api.open-meteo.com/v1/forecast` с текущими значениями, почасовыми (49 значений) и дневными максимумом и минимумом; время в unixtime. Осадки в почасовых данных относятся к предыдущему часу, поэтому для столбца часа T берётся запись T+1. Координаты в запросе округляются до 0,01° (около 1 км). Заголовок User-Agent: `PogodaApp/<версия>`.
- Условия Open-Meteo: данные под лицензией CC BY 4.0; ссылка «Weather data by Open-Meteo.com» на https://open-meteo.com/ должна стоять рядом с каждым местом, где показаны данные (https://open-meteo.com/en/licence). Сейчас она в нижней строке главной; на новых вкладках с данными нужна такая же. Бесплатный доступ только для некоммерческого использования, до 10 000 запросов в день (https://open-meteo.com/en/terms).
- Место: системный `LocationManager`, только `ACCESS_COARSE_LOCATION`. Последнее известное место (`getLastKnownLocation` у FUSED и NETWORK, берётся более новое) отвечает сразу. Свежее место (`getCurrentLocation`) запрашивается у FUSED и NETWORK одновременно, побеждает первый ответивший, общий предел 10 с. Название города через `Geocoder`, если не получилось, «Текущее место».
- Порядок загрузки на главной (с версии 0.1.1): показываются сохранённые данные; прогноз запрашивается сразу по последнему известному месту, не дожидаясь свежего; свежее место определяется параллельно, и если оно дальше 2 км от первого, прогноз запрашивается ещё раз (неудача второго запроса не затирает показанное); название места ищется параллельно с запросом прогноза и дописывается, когда готово (запоздалое название прежнего места не заменяет текущее). До 0.1.0 прогноз ждал свежего места (до 10 с на поставщика подряд), а название ждало прогноза: Дима 28.10.2026 пожаловался, что данные грузятся долго.
- Обновление: при открытии приложения, если данным больше 15 минут или есть ошибка; сохранённый прогноз показывается сразу и лежит в `files/forecast_cache.json`. Название из сохранённого берётся, если место сместилось меньше чем на 2 км.
- Обновление протягиванием (с версии 0.1.2): `HomeViewModel.refresh()` заново определяет место и грузит прогноз, не глядя на 15 минут; флаг `refreshing` держит индикатор, он виден не меньше 700 мс; повторное протягивание во время обновления игнорируется. Жест написан на обычной вложенной прокрутке (`NestedScrollConnection` в `ui/components/PullRefresh.kt`), без пробных функций Material 3 (иначе сборка с «предупреждения как ошибки» требует отдельного допуска, а их стабильность в версии библиотеки не проверена). Порог 64 dp сдвига (палец проходит вдвое больше, около 2 см), удержание 56 dp, предел 100 dp; сдвигается только верхняя часть экрана, лента «По часам» и панель стоят. Проверка на эмуляторе (`emulator_smoke.sh`, пункт 3б): короткое движение (около 45 dp пальцем) обновление не запускает; длинное запускает (по строке `PogodaRefresh` в журнале). Чтобы успеть увидеть обновление, проверочная сборка (только debug) читает из папки приложения файл `location_delay_ms.txt` и на столько миллисекунд замедляет определение свежего места (сценарий ставит 12 000). Пока обновление идёт, проверка требует сдвиг верха экрана на 56 dp и подпись индикатора «Refreshing…», потом возврат на место и исчезновение индикатора. Снимки «3б-…» лежат в ветке `ci-screenshots`.
- Цвета мелкого текста: Ink2; Ink3 не проходит 4,5 : 1 на стекле и небе и мелким текстом не используется (проверяет `PaletteContrastTest`).
- Положение крупной цифры и градуса считается от базовой линии шрифта Manrope так же, как в макете (Compose иначе ставит первую строку по полной высоте шрифта).

## Ограничения среды Claude
- Из сессии недоступны Android SDK, Maven и Gradle (403 на узлах Google и Gradle), поэтому настоящий тест сборки делает GitHub Actions.
- Команды `gh release …` из сессии не работают (используют GraphQL, он закрыт, 403): выпуски читать через `gh api repos/dumahuch/weather/releases`.
- Журналы запусков GitHub из сессии не скачиваются: `gh api .../actions/jobs/<id>/logs` перенаправляет на хранилище `*.blob.core.windows.net`, его нет в списке разрешённых узлов сессии (403). Поэтому проверки сами выкладывают нужные журналы в ветку `ci-screenshots` (пункт 7 выше). Расширить список узлов можно в настройках среды (claude.ai/code → меню у названия сессии → «Edit cloud environment» → Network access → Custom), но это открывает любые хранилища Azure, поэтому не сделано.
- Запросы к API запусков Actions, отправка меток и удаление веток и меток через сессию запрещены (403). Результаты читаются через проверки коммита: `repos/dumahuch/weather/commits/<sha>/check-runs` и их аннотации (сценарий `annotate_failure.py` выводит причины падения в аннотации).
- Ветка `ci-probe` осталась от пробного запуска, Claude удалить её не может. Дима может удалить сам: GitHub → Branches → корзина у `ci-probe`. Ветки `design-materials` и `step-1` (слиты в main) тоже не удалены. Ветка `ci-screenshots` служебная (снимки экрана проверок), создаётся заново при каждой проверке ветки `step-*`.

## Проверка разработчиков Android (Google)
- Принудительная проверка с 30 сентября 2026 в Бразилии, Индонезии, Сингапуре и Таиланде, в остальных странах «в 2027 году». Германия отдельно в официальном описании не названа (проверено 28.10.2026): https://developer.android.com/developer-verification/guides.
- Для приложений «себе и друзьям» есть бесплатный аккаунт «ограниченное распространение»: до 20 устройств, без проверки личности; нужны Google-аккаунт с двухэтапной проверкой и платёжный профиль.
- Источники: https://developer.android.com/developer-verification/guides/limited-distribution, https://android-developers.googleblog.com/2026/03/android-developer-verification.html.
- Решение для Димы: зарегистрироваться заранее, до включения проверки в Германии (по официальной странице не раньше 2027 года).
